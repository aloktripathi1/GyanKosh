# Why I built GyanKosh the way I did

This is my own account of the decisions behind this project, written the way I'd actually explain it if someone asked me to defend a choice out loud. The README says what the system does. This is about why it ended up looking like this, including the parts that didn't go smoothly the first time.

## The orchestrator: custom, not a framework

The core of this project is a 10-stage pipeline that has to survive partial failure, resume from wherever it left off, and run four of its stages at once instead of one after another. I had to decide how to coordinate that.

I considered LangGraph, since it's built for exactly this kind of multi-step LLM pipeline and would have given me a lot of the checkpointing machinery for free. I also considered a real workflow engine like Temporal or Airflow, since checkpoint-and-resume is a solved problem there. I ended up writing my own orchestrator instead, a plain Python state machine backed by a `jobs` table in Postgres, and I'd make the same call again for a project this size. My reasoning was that I had four days, the pipeline is basically linear with one real fan-out point, and I would rather spend that time understanding and testing my own fifty lines of retry and checkpoint logic than debugging someone else's framework under deadline pressure. If someone asks me how resume-from-checkpoint actually works, I can point at `next_stage()` in `pipeline.py` and walk through it line by line, which is exactly the kind of thing I wanted to be true going into an evaluation. The tradeoff is real: a mature framework would have given me retry policies, observability, and distributed execution I had to build myself, and if this pipeline grew past ten stages or needed real horizontal scaling, I'd hit the ceiling of what a hand-rolled orchestrator can reasonably handle. For this scope, I think I picked correctly.

For the database, I used Postgres with JSONB columns rather than a pure relational schema or a document database like MongoDB. The job state itself, status, current stage, progress percentage, is genuinely relational and benefits from real transactions. But the actual stage outputs are LLM-generated structured data whose shape kept changing while I was building this, new fields on the Period schema, an added teaching_context field, and so on. If I'd modeled every nested field as its own relational column I would have been writing a new migration every time I tweaked a prompt. JSONB let me keep the flexibility of a document store for that part while keeping one database instead of running Postgres and Mongo side by side for no good reason. The Pydantic schema is still the actual source of truth for validation, the JSONB column is just storage.

For the API, I used REST instead of GraphQL. There's no client here that needs to compose complex nested queries across resources, it's upload a document, poll a job, fetch a TKP, regenerate one section. GraphQL would have added a schema layer and a resolver graph for a set of endpoints that are already about as simple as they can be.

For progress updates, I used Server-Sent Events instead of WebSockets or plain polling. I only need to push state in one direction, server to client, so SSE is the layer that gives me the minimum amount of protocol for the job. I'll admit the actual implementation is not the elegant version of SSE, it's a loop that polls the jobs row every two seconds and only emits an event when something changed, rather than a true database-level push via Postgres LISTEN/NOTIFY. I chose that because it was fast to build and correct to reason about, and two-second latency on a job that runs for minutes doesn't matter to a person watching a progress bar. If this needed to scale to a lot of concurrent jobs I'd revisit it, but at this scale the honest answer is that a database is being asked "did anything change" once every two seconds per open connection, and that's fine.

## Auth: one API key, deliberately not more

I decided against building real user accounts even once the core pipeline was working and I had time left. The reasoning is that the assignment doesn't ask for multi-tenancy, and every job and TKP already gets written to Postgres the moment it's created, so a user doesn't lose their work by not being logged in, they just don't have a login. What auth would actually buy at that point is isolating one person's documents from another's, and there is exactly one person using this thing during evaluation. Building real accounts, sessions, and per-user data scoping would have been real, nontrivial surface area, and it's exactly the kind of scope creep the assignment's own instructions already told me not to do. What I built instead, once I noticed the actual gap was "I can't see my past runs," was a Library view that lists every job by document name, subject, and status, which solves the problem people actually have without needing a login system to do it.

## Storage: an interface first, S3 later

Files are stored on local disk right now, but every access to them goes through a `StorageBackend` interface, not direct filesystem calls, and I made that decision from the start rather than retrofitting it. The reason is that on Render's free tier, local disk doesn't persist across a redeploy, so it's genuinely not a production storage strategy, but building real S3 support up front would have meant setting up an AWS account, credentials, and a bucket before I even had a working pipeline to store anything with. The interface means swapping to S3 later is one new class implementing four methods, not a rewrite of every caller. I did this same interface-then-implementation split for the LLM client and the storage backend for the same reason: I wanted the parts of the system likely to change in a real deployment to be swappable without touching the pipeline logic around them.

## PDF generation: WeasyPrint over a raw PDF library

I needed to generate three different PDF documents, lesson plans, a teacher guide, and an assessment book, each with its own layout. I used WeasyPrint, which renders HTML and CSS to PDF, instead of a library like ReportLab where you position text and boxes directly. Styling three documents with CSS, page breaks, typography, tables, was much faster to iterate on than doing absolute positioning by hand, and I could reuse ordinary web layout knowledge instead of learning a new drawing API. The cost was WeasyPrint's own dependency footprint, and I had to pin `pydyf==0.10.0` specifically because a newer version broke compatibility. That's a small tax I was willing to pay for the iteration speed.

## Cutting cost: routing, caching, and not re-billing the same document

Every LLM call in this pipeline goes through one function, `structured_call` in `llm/client.py`, and that let me apply cost controls in one place instead of scattered across eight agents.

The first control is model tiering. Classification and knowledge extraction are closer to structured parsing than to generation, so they go to Haiku. Planning, content generation, activity generation, assessment generation, and gap analysis actually require reasoning about pedagogy, so they go to Sonnet. This isn't a blanket "use the expensive model everywhere" or "use the cheap model everywhere" policy, it's tied to which stages actually need the stronger model's judgment.

The second is prompt caching. The system prompt and tool schema for a given stage don't change between calls, only the document content does, so I mark the system prompt block as `cache_control: ephemeral`. That pays off specifically on retries, since a failed attempt retrying the same stage hits a cache instead of paying full price again, and it also pays off across different documents hitting the same stage within the cache window.

The third is caching by document content hash. If someone uploads the exact same file twice, and this happens more than you'd think during testing, since I re-uploaded the same NCERT chapter dozens of times this session, there's no reason to re-run document intelligence, classification, and knowledge extraction against identical bytes. I hash the upload with SHA256 and, if a prior job exists for that hash, seed the new job's checkpointed state with those three stages already filled in. Generation stages still run fresh, since regenerating with a teacher's context or after a fix should actually produce new content, but the expensive early stages don't get re-billed for no reason.

## Making it faster: running four stages at once

Content generation, activity generation, assessment generation, and gap analysis don't depend on each other, they only depend on the teaching plan and the knowledge extraction that already happened. Originally they ran one after another because that's the simplest thing to write first. Once the pipeline was working end to end, I changed that to run all four concurrently using a `ThreadPoolExecutor`, since they're I/O-bound waiting on the Anthropic API, not CPU-bound.

I have real numbers on what this saved. On one Physics chapter run, the four stages individually took 74.78, 36.65, 119.66, and 7.62 seconds, which sums to about 239 seconds if run one after another. Run concurrently, the batch takes as long as the slowest one, 119.66 seconds in that case, so the parallel version cut that portion of the pipeline roughly in half. On smaller test documents I measured the whole pipeline going from about 180 seconds before this change to somewhere between 61 and 86 seconds after, which is closer to a 2 to 3x improvement on total wall time, since on a smaller document the parallel batch is a bigger fraction of the total run.

This change is also what caused the worst bug I hit this whole project, which I'll get to below.

## Grounding: checking against the source, not asking a second model

The most important non-functional requirement here, more important to me than speed, was that nothing in the output should be something the model made up. I considered the obvious alternative, having a second LLM call review the first one's output and flag anything that looks hallucinated. I decided against that because it doesn't actually solve the problem, it just adds another model that can also be wrong, and now I have two unreliable checks instead of one, with no way to know which one to trust when they disagree.

What I built instead traces every factual claim back to an actual location in the source document. In stage 3, every extracted objective, concept, definition, formula, and misconception has to come with a verbatim quote and the exact section it came from. Every later stage that generates something, a checkpoint question, an activity, an assessment item, has to cite which of those stage 3 items it's grounded in, using a real quote, not a paraphrase. I resolve that citation against the actual document using a tiered match, exact string match first, then a whitespace-normalized match, then a fuzzy match with `rapidfuzz` as a fallback for cases where the model quotes something correctly but with minor formatting drift. If none of those match, the citation is rejected and the stage fails and retries.

This is a stricter design than "ask the model to be careful," and it has a real cost, which I found out directly while building the sample outputs, described below. But I'd rather have a system that sometimes fails a stage because it can't prove a claim is grounded than one that publishes a plausible-sounding sentence nobody checked.

## The bug that actually took the longest to find

While generating a sample from a humanities document, four separate live attempts against the deployed backend hung. Not crashed, not errored, just sat at "running" forever with no progress and no error message. That's a much worse failure mode than a crash, because a crash tells you where to look.

The parallel stage change was the newest thing I'd touched, so I started there. The actual cause was in SQLAlchemy, not in my own pipeline logic directly. By default, a SQLAlchemy session marks every attribute on a committed object as stale after `commit()`, so the next read of that attribute triggers a fresh query. The orchestrator commits after every stage completes. Right before spawning the four parallel worker threads, the pipeline had just committed. Each of those four threads then read `job.stage_results` for the first time after that commit, which meant four threads simultaneously tried to lazily reload the same attribute against the same shared database session. SQLAlchemy sessions are not safe for concurrent use from multiple threads, and what I got instead of a clean error was several threads all contending for one connection with nothing resolving.

The fix was one line, setting `expire_on_commit=False` on the sessionmaker, so a commit stops invalidating already-loaded data and nothing needs to be re-fetched from inside a worker thread. But finding a one-line fix for a hang took real time, because a hang doesn't leave a stack trace pointing at the problem the way an exception does.

Once I understood the cause, I didn't stop at fixing that one case. I added a hard timeout around every stage, sequential or parallel, so if something hangs for a reason I haven't anticipated, the stage fails explicitly after ten minutes instead of leaving a job stuck forever. A Python thread that's genuinely stuck can't be forcibly killed, so the executor shuts down without waiting for it rather than blocking cleanup on a thread that may never return. I proved this actually works, not just that it looks right, by writing a test where a stage's mocked agent call is `threading.Event().wait()` with nothing ever calling `.set()`, a function that by construction never returns on its own, and asserting the orchestrator still fails the job within the bounded time. Then I went back and re-ran the exact document type that had originally hung, twice more, specifically to confirm the fix generalized and I wasn't just trusting the unit test.

## Two more bugs, found by testing on documents I hadn't tried before

Everything up to that point had mostly been tested against Chemistry content. When I generated the History sample, two more real bugs showed up that Chemistry alone had never triggered.

The first was a schema shape mismatch. The gap analysis stage's output schema has one top-level field, a list called `gaps`. On one run, the model's tool-use response came back as `{"gaps": {"gaps": [...]}}`, the list wrapped in an extra dict with the same key name, instead of `{"gaps": [...]}` directly. Pydantic validation failed immediately with a clear type error, which was at least easy to diagnose. I'd already built a repair step for a related problem, where a nested list field sometimes arrives as a JSON string instead of an actual list, so I extended that same repair layer with a schema-aware check, if a field is declared as a list type and the value is a dict with exactly one key whose value is a list, unwrap it. I kept that narrow on purpose, checking against the actual Pydantic field types rather than guessing based on key names, so it can't accidentally mangle a field that's legitimately supposed to be a dict.

The second was more interesting because it wasn't really a bug in my code at all. On a retry after the schema fix, gap analysis failed again, this time because it burned through all three retries hitting the grounding check. The system prompt for that stage tells the model to copy citations verbatim into a `grounding_refs` list, one entry per fact. Instead, the model combined several separate facts into one synthesized sentence and put that whole sentence in as a single citation. The grounding resolver correctly couldn't match that combined sentence against any single stage 3 item, because it wasn't actually a verbatim quote of anything, it was a summary. That's the grounding check doing exactly what it's supposed to do, refusing to accept a citation that doesn't trace to a real source. The cost is that it burned through all three retries before I noticed the pattern, since a wrong-but-plausible combined sentence can come out on more than one attempt. I fixed it by making the prompt explicit that if a misconception draws on multiple facts, each one needs to be its own separate entry in the list, never merged into one string, and after that the same failure mode stopped recurring across repeated runs.

I'm including that second one specifically because it would have been easy to read the error and assume the grounding check itself was broken and needed to be loosened. It wasn't. The check was correct, the prompt was underspecified, and loosening the check to stop the retries from burning would have meant accepting less reliable citations everywhere, not just fixing this one case.

## A real security bug, found by auditing, not by an attacker

Late in the project I went back through the storage layer specifically looking for anything I'd normally flag in someone else's code. The local storage backend resolved a requested file path by joining it onto a base directory with no check that the result actually stayed inside that directory. A path containing `../` segments, which reaches that function directly from the `GET /files/{path}` URL, could walk outside the intended storage root. I fixed it by resolving the path and explicitly verifying it's still a descendant of the base directory before allowing a read, write, or delete, raising a specific error otherwise. While I was in that file I also fixed a related but separate issue, download links used a single static API key as a query parameter with no expiration, so I replaced that with HMAC-signed URLs that carry their own expiry and get regenerated fresh every time a TKP is fetched, rather than one link that would work forever if it ever leaked into a browser history or a log file.

## Testing across three different subjects, not just one

I tested this pipeline against real NCERT chapters in Chemistry, History, and Physics, not synthetic test documents and not just one subject run twice. That choice is directly why I found the two gap analysis bugs above, since neither one showed up on Chemistry content. It also let me check something I actually cared about, whether the system was forcing the same shape onto every subject regardless of fit. It wasn't: History produced periods sequenced around thematic and chronological relationships with almost no numerical assessment questions, while Physics produced a period-by-period build toward circuit calculations with numerical questions in most periods, and I hand-checked every one of those calculations myself rather than trusting that a plausible-looking number was a correct one.

The other piece of testing I want to call out is a live database concurrency test, because it's the one test in the suite that's actually proving something a unit test can't. The regenerate-section endpoint locks a TKP row with `SELECT ... FOR UPDATE` so two concurrent regenerate calls can't race each other. Every other test in this project deliberately avoids needing a real Postgres connection, mocking the database boundary the same way the LLM boundary gets mocked, since that keeps the suite fast and independent of infrastructure. But you cannot prove a row lock actually blocks a second transaction by mocking the database, you can only prove your code called the right method and trust that it works. So for this one test I actually opened two real threads, each with its own real connection to a real Postgres instance, and had one hold the lock for a fixed duration while measuring how long the second one waited before it could proceed, on the second thread's own clock rather than comparing timestamps across threads, which I initially tried and had to abandon because comparing wall-clock timestamps recorded on two independent threads turned out to be racy under normal OS scheduling jitter even when the underlying database ordering was completely correct. I didn't have Docker or sudo access in the environment I was working in, so I downloaded the Postgres 18 packages directly with `apt-get download` and extracted them without installing anything system-wide, just to have something real to test against instead of leaving this as a documented limitation I couldn't actually verify.

## What I decided not to build

A few things were explicitly out of scope, and I want to be clear these were decisions, not things I ran out of time for.

Multilingual generation, curriculum-board alignment to something like CBSE or Common Core, and horizontal scaling past one worker and one database instance were all cut early, before I'd written any code for them, because none of them are part of what's actually being evaluated here and each one is a real project on its own, not a small addition. Full multi-tenant auth I addressed above. In every one of these cases the honest reason is the same: the four days I had were better spent making the ten stages that are actually required work reliably across different subjects than adding breadth that isn't being asked for. If I'd built a thinner version of all four of those instead of a solid version of the core pipeline, I don't think that would have been a better use of the time, even though it might have made the feature list longer.
